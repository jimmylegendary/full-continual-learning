## 2. 설계 판단과 근거

### 2.1 P0을 phase에서 없앤 이유

**USER (B17):** 조사·spike만 하는 phase와 한 계층만 만드는 phase는 금지다. 옛 P0은 용어·state clocks·source boundary·baselines·평가 split·budget을 정하는 계약 전용 phase였다. 이 항목들은 P1의 작업이 시작되기 전에 필요하다는 점에서 순서는 맞았고, 틀린 것은 그것이 phase였다는 점이다. 그래서 순서는 보존하고 지위만 바꿨다. 용어·시계·source는 T01, 평가 split·oracle 분리는 T02, baseline·budget은 T03, 세계 생성기는 T06이다. 각 작업에 "실패하는 테스트가 존재한다", "무정보 learner가 chance다" 같은 완료 판정을 줘서 "문서만 쓰고 끝"을 막았다.

### 2.2 "agent 제품은 CLI에서 실제 LLM으로 실제 일을" 규칙을 FCL에 적용한 방식

근거 문서는 다음과 같다. **USER:** B17(규칙 원문), U-T07의 통합 System ONE 정정, B13("벌써 agent에 연결해?")·B14(agent 연결 구조에 치우침), B12(실제 codex·prime agent 연동이 목표). **LITERATURE:** [01-intent-and-charter.md](/home/jimmy/repos/full-continual-learning/docs/01-intent-and-charter.md) §5(외부 frozen LLM 프롬프트 앞에 원문을 붙이는 성공을 최종 시스템으로 바꾸지 않되 강한 대조군으로 유지), [05-integrated-architecture.md](/home/jimmy/repos/full-continual-learning/docs/05-integrated-architecture.md) §3(별도 fast model을 최종 제품으로 전제하지 않음), [AGENTS.md](/home/jimmy/repos/full-continual-learning/AGENTS.md)(정정을 되돌리지 않음).

검토한 해석은 셋이다.

| 해석 | 판단 |
|---|---|
| (a) 규칙을 FCL에 적용하지 않는다. 라이브러리 단위 테스트로 phase를 닫는다 | 기각. mock-only·분리된 module 테스트를 완료로 보지 않는 것이 규칙의 핵심이고, 옛 P1의 "완료로 부르면 안 되는 것"과도 같다 |
| (b) FCL을 처음부터 codex·prime agent 안에 넣어 "실제 agent 작업"으로 닫는다 | 기각. B13·B14의 비판 대상이고, 효용 근거 없이 연결 구조·interface부터 만드는 것이다. 또 FCL 모델은 아직 구현 전이라 agent에 붙일 대상이 없다 |
| (c) 규칙의 정신(실제 인터페이스·실제 의존성·처음부터 끝까지)을 모델 제품에 맞게 옮긴다 | 채택. "실제 LLM" = retrofit한 모델 자체, "실제 인터페이스" = `fcl` CLI 세션, "실제 일" = 새 개체 질문에 답하고 반례를 받아 고치고 재시작 뒤에도 유지하는 여정. 외부 agent 연결은 consumer를 넓히는 P5의 넓이 확장 |

주의할 점이 하나 있다. "실제 일"을 합성 세계의 질의로 정했기 때문에 사용자가 "실제 사용자 작업"을 기대했다면 괴리가 생긴다. 이 괴리는 §2.3의 후보 (d)(자연어 소규모 관계 그래프)와 P5의 자연어 혼합 도메인으로 줄이되 P1에서는 하지 않는다(사전지식 오염·평가 모호성 때문). 이것은 D-03·D-09에 걸린 OPEN이다.

### 2.4 대조군을 P1에 둔 이유

- **LITERATURE:** review §4.1은 읽은 11편 어디에서도 학습된 schema 구조가 같은 예산의 고정·무구조 대조보다 낫다는 직접 비교를 찾지 못했고, HWU20(구조 없는 변형이 더 높음)·GOUDAR23(동결 망이 비슷함)·ELDER26(큰 MLP가 더 높음)은 오히려 단순 대조가 비슷하거나 낫다고 보고한다. review §5-8은 "모든 기제는 §4.1의 대조와 함께 판정한다"를 공통 규칙으로 둔다.
- **ARCHIVE:** Melete에도 대조는 있었다(N1의 matched 비교, J1의 고정 graph·graph 없음 대조). 그 결과가 독립 기여 미입증(0.48%, 대략 95% 구간 −3.07~4.04%)과 seed7 pilot의 열세였고, 문제는 효용 gate가 다음 단계의 진입 조건으로 집행되지 못했다는 것이었다(Melete 스스로의 진단). 그래서 FCL은 대조군의 존재와 gate의 집행을 둘 다 P1에 넣는다.
- **늦게 넣을 때의 문제:** 나중에 대조군을 붙이면 같은 예산·같은 경로 보장이 깨지고, 그 사이 쌓인 구현 PASS가 효용으로 읽힌다. `--arm` 하나로 같은 CLI·같은 session 프로토콜·같은 runtime 경로를 쓰면 P1에서 넣는 비용이 작다.
- **arm 설계 근거:** `fixed`(학습한 구조의 기여를 분리), `flat`(분해 구조의 기여를 분리), `always`(gate의 기여를 분리, review §5-2의 "항상 쓰기" 대조), `ctx`(raw history의 강한 대조, docs/01 §5·docs/08 §4), `base`(floor). 정직한 한계: `flat`의 구체 정의는 retrofit 설계가 확정돼야 쓸 수 있어서 P1-T03에서 결과를 보기 전에 봉인하도록 했다. `ctx`는 prompt token 때문에 계산 예산이 달라 "같은 예산 대조"가 아니라 참고 대조로 표기한다.

### 2.5 sealed readout을 P1에 넣고 등급을 2로 상한한 이유

- **집행 문제:** Melete는 구현 PASS와 효용 PASS를 문서로는 구분했지만 다음 단계 진입 조건으로 집행하지 못했다. 집행하려면 phase 안에 사전 명세 readout이 있어야 한다. 그래서 P1-T14(봉인)·T15(readout)를 넣고 §7에 진입 규칙을 두었다. 대안(D-07 (b), dev pilot까지만)은 가볍지만 P1 → P2 진입에 효용 gate가 없다.
- **P1 종료와 효용의 관계:** P1 종료 gate는 readout의 PASS를 요구하지 않고 "상태를 기록한다"를 요구한다. PASS가 아니면 P1은 종료 선언이 아니라 §7 분기로 간다. 제품은 돌아가는데 주장은 지지되지 않는 상태를 "완료"라고 부르지 않기 위한 설계다.
- **등급 사다리:** 등급은 증거의 범위를 말하고 결과 상태(PASS/FAIL)는 방향을 말한다. 두 축을 분리하면 높은 등급의 FAIL도 강한 증거가 된다. 등급은 "범위 제한자"를 풀 때마다 오른다: 등급 2 = 합성·단일 구조 family·소형 모델 1종·제한 seed, 등급 3 = 구조 family 2종 이상 + 사전 명세 충분 seed + 봉인·fresh cohort·독립 검토, 등급 4 = 모델 2종 이상 + 자연어 혼합 도메인 + 복제, 등급 5 = 실제 consumer·다세션·관측 coverage. P1은 모든 제한자가 걸려 있어서 사전 명세 readout이 PASS여도 등급 2다. 사용자 요구("사전 명세한 통계로 확인되기 전에는 schema 이득이라 쓰지 않는다")는 필요조건으로 지켜지고, 우리는 등급 3 범위 조건을 더 얹어 더 엄격하게 했다.
- **수치를 만들지 않은 이유:** [08-evaluation.md](/home/jimmy/repos/full-continual-learning/docs/08-evaluation.md) §6·§7은 목표치를 pilot variability와 실용 요구로 prospective하게 확정하고, 결과를 본 뒤 threshold·margin·subset을 고치지 않는다고 한다. 그래서 효과 크기·seed 수·예산 허용오차는 P1-T14에서 dev pilot 분산으로 처음 정하게 했다. Melete J1의 5pp·표본 계획·보정 수치는 이식하지 않았다(그 값은 Melete의 pilot 맥락의 것이다).
- **한계:** 문구 검사기는 낱말 수준의 검사라 의미 오용을 막지 못한다. 그래서 등급 3 이상은 독립 검토를 요구한다.

### 2.6 "해당 source의 수정/삭제 처리"를 P1에 얇게 넣은 판단

판단: **fast state 한정으로 P1에 넣는다(D-06에서 사용자 확인).** 근거는 다음과 같다. ① 규칙은 저장·검증 경로 같은 뼈대가 P1부터 실제로 있기를 요구하고, source ledger와 snapshot 재생은 그 뼈대의 일부인데 삭제가 그것을 시험하는 가장 싼 방법이다. ② Melete의 제품 P1도 재시작·삭제를 종료 gate에 넣었다. ③ P1에는 Sleep·slow 통합이 없어서 모든 학습 상태가 fast state에 있고, 원장에서 source를 철회한 뒤 committed snapshot에서 남은 source를 같은 순서로 재생하면 "그 source 없이 처음부터 만든 state"를 정확히(허용오차 안에서) 재구성할 수 있다. 이것은 [07-state-and-storage.md](/home/jimmy/repos/full-continual-learning/docs/07-state-and-storage.md) §6("병합 후에는 개별 source 삭제가 완벽히 가능한지 검증 없이 약속하지 않는다")과 충돌하지 않는다. 병합(통합)이 아직 없는 범위만 약속하기 때문이다.

정직한 상한: 통합된 weights에서의 삭제는 P4에서 "측정만", P5에서 "검증한 범위만"이다. 수정은 "삭제 + 같은 위치에 다시 삽입"으로 정의했고 반례·정정(국소 갱신)과는 다른 단계다. 일정·계산이 넘치면 범위 절삭 순서의 첫 항목으로 P2에 넘긴다.

### 2.7 H1–H5의 메커니즘이 어느 phase·capability로 계승되는가

### 2.8 phase 경계를 이렇게 고른 이유

| 대안 | 판단 |
|---|---|
| A. 계층별(재귀 → controller → Sleep → 확대 → 외부화, 옛 방식) | 규칙 위반: 한 계층만 만드는 phase |
| B. 능력을 하나씩 완성한 뒤 조립 | 규칙 위반: 부품을 완성해 마지막에 조립 |
| C. 같은 조각의 시간순 성숙(prototype → alpha → beta) | 무엇이 올라가는지(넓이·깊이)가 불명확해 해상도 상승으로 검증할 수 없다 |
| **D. 전체 여정 × 해상도, 경계는 "사용자가 새로 할 수 있게 되는 것"** | 채택 |

경계는 U-T07의 세 행동을 여정으로 번역한 것이다. 익숙하면 빠른 schema 기반 답, 덜 익숙하면 rapid learning 후 답, 더 낯서면 깊은 loop. P1은 rapid learning 경로를 전체 여정으로, P2는 깊은 loop 축을, P3는 셋 사이를 고르는 controller를, P4는 깊은 사고가 빠른 판단으로 굳는 Sleep을, P5는 범위와 연결을 올린다.

순서의 근거는 다음과 같다. 고정 깊이 곡선이 controller보다 먼저다(review §5-6, 옛 §3 순서 유지). Sleep은 깊이 곡선과 controller 뒤다(replay 예산 배분과 deep-to-shallow를 비교할 기준선이 필요하다). 외부화 v0는 Sleep과 함께다(bundle에 slow level이 들어가야 의미가 있다). 외부 agent 연결은 마지막이다(B13). phase 수는 5로 했다. 4 이하이면 P2에 재귀와 controller가 몰리고, 6 이상이면 가장 먼 P5를 미리 쪼개게 되는데 P5는 P4 종료 재검토에서 쪼갤지 결정하는 편이 점진적 상세도 원칙에 맞다. 각 phase에는 spike를 앞쪽 작업으로 두고 "spike가 실패하면 그 능력을 다음 phase로 이월하고 현 phase는 나머지로 종료한다"는 규칙을 둬서 한 phase가 막혀도 제품이 계속 돌게 했다.

### 2.9 결과 등급 상한의 설계

세 축을 분리했다. gate 종류(Contract·Efficacy·Product, docs/08 §1), 결과 상태(PASS·FAIL·INCONCLUSIVE·BLOCKED·NOT RUN, docs/08 §8), 증거 등급(0–5). 등급이 오르는 조건은 범위 제한자(합성·단일 family·단일 모델·제한 seed)를 푸는 것과 확증 방법(봉인·fresh cohort·독립 검토)을 갖추는 것이다. 허용·금지 문구를 등급마다 적고 결과 보고 생성기가 등급 필드를 필수로 찍게 했다. phase별 최대 등급은 P1 2, P2~P4 3, P5 4(운용은 관측 coverage 안에서 5)이고 주장 단위로 부여한다.

### 2.10 P1의 크기와 절삭

P1은 작업 16개로 "가장 얇은 MVP"치고 크다. 판단은 이렇다. 사용자가 요구한 P1 내용(전체 여정 + 대조군 + 망각·표면/구조 + 실제 가중치·갱신·재시작)이 이미 크고, 작업을 줄이면 그중 하나가 빠진다. 대신 절삭 순서를 정해 놨다: T13(삭제) → readout seed 수 축소. 절삭하지 않는 것은 실제 CLI E2E, 고정·무구조·항상-갱신 대조, 망각·표면/구조 평가다. P1-T05가 실패하면 NMM을 빼고 CMS 분기만으로 P1을 닫되 문구에 밝힌다.
